# User CRUD admin API

## Problem statement

Admins need HTTP endpoints to manage users. Last-admin guard must be enforced server-side regardless of UI gating.

## Scope

In scope:
- `GET /api/v1/users` (list), `POST /api/v1/users` (create — returns one-time setup URL once), `PATCH /api/v1/users/{id}` (name, email, role).
- `POST /api/v1/users/{id}/disable`, `POST /api/v1/users/{id}/enable`.
- `POST /api/v1/users/{id}/setup-link` (regenerate; invalidates prior token AND clears `password_hash`).
- All endpoints admin-only (return 403 to non-admins, even though no non-admins exist day one).

Out of scope:
- Frontend (covered by `frontend_settings_users`).
- Audit logging (deferred).

## Acceptance criteria

- Non-admin requests → 403.
- Last-admin guard returns HTTP 409 on disable, role change, or email-change-which-disables-current.
- `POST /users` response body contains the raw setup URL once; the URL token hashes to the stored `token_hash`.
- Regenerate-link clears `password_hash` AND marks any prior unused token as expired.
- Email update creates a new row, disables the old (per spec R3).

## Quality gates

- Integration tests cover: list, create + setup URL retrieval, edit, disable, enable, regenerate, last-admin guard on every applicable action, email-change-creates-new-row.
- Lint and format pass.
