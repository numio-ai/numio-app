# User Management — native backend, single role

## Problem statement

Numio ships with a synthetic admin (`admin@localhost`) injected by bypass-mode auth, and the frontend renders a hard-coded dummy user "James C. admin". Real teams cannot sign in, cannot be added, and cannot be removed. Without real user management Numio cannot move past single-operator demos.

## Objective

A team of 5–20 users sharing one Numio install — primarily cloud-hosted on the customer's AWS account, occasionally a single-operator laptop — can bootstrap the first admin during install, add and remove other users from the UI, sign in concurrently from their own browsers, and change their own profile.

This phase delivers the native identity backend and a single role (`admin`). Cognito and richer roles are deferred to feature `user_management_extensions`.

## Acceptance criteria

A1. Fresh install with `AUTH_BYPASS=false` (native backend) lands the user on a "Create first admin" screen. Completing the form signs the user in as that admin.
A2. Signed-in admin uses `Settings → Users` to add a second user. The UI returns a one-time setup URL. Pasting that URL in a private window lets the new user set a password and lands them signed in.
A3. An admin disables a user. That user's existing session survives until expiry but they cannot sign in again. Re-enabling restores sign-in.
A4. With one active admin, Disable and role-change actions on that admin are greyed out with a tooltip. Direct API calls return HTTP 409.
A5. Any logged-in user can change their own name and password from a profile page that does not expose email or role edit. The page displays the active workspace UUID read-only.
A6. `AUTH_BYPASS=true` with `ENVIRONMENT=production` prevents backend startup with a clear error.
A7. `AUTH_BYPASS=true` with `ENVIRONMENT=local` works exactly as today: synthetic admin, no `Settings → Users`, no real user rows touched.
A8. The `cognito` identity backend code compiles and tests pass — dormant but not deleted.

## Scope

In scope:
- Native identity backend (email + password in Postgres)
- First-run create-first-admin flow
- User CRUD UI with single role `admin`
- Self-service profile (name, password, read-only workspace ID)
- Server-side sessions, sliding 24h TTL
- One-time setup links (admin issues, copy-paste, no email)
- `AUTH_BYPASS` rename and environment gate
- Doc updates: `docs/dev-runbook.md`, `docs/ops-runbook.md`

Out of scope (tracked under `user_management_extensions`):
- Cognito wiring, audit log, machine users / API tokens
- Roles beyond `admin`
- Mid-session forced sign-out, SMTP, self-serve forgot password, account lockout
