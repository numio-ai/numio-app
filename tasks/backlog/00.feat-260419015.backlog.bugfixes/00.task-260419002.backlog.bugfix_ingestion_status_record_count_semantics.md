# `ingestion-status.record_count` does not match `cost_records` row count

**Date:** 2026-04-18

## Observed problem

`GET /api/v1/jobs/ingestion-status` reports a `record_count` that is not the number of rows in `cost_records`. Repro on the test account (`123456789012`) after a single successful `cur_ingestion` run:

- `ingestion-status.record_count` = **3698**
- `SELECT COUNT(*) FROM cost_records WHERE provider='aws' AND data_source='cur'` = **678**

Ratio ~5.4:1 suggests `record_count` is counting rows *processed* (including duplicates deduped by `(data_source, line_item_id)` and/or upsert re-writes) rather than rows *persisted*. The field name implies the latter.

## Expected vs actual

| | Expected | Actual |
|---|----------|--------|
| `record_count` semantics | Number of rows landed in `cost_records` for this data source (stable across reruns of the same billing period) | Number of rows processed from the CUR parquet(s), inflated by duplicates/upserts |
| Correspondence | Sum of `record_count` across ingestion runs ≈ row count in `cost_records` | Large discrepancy even after a single run |

## Reproduction steps

1. Fresh install, single connected AWS account with real CUR export.
2. `POST /api/v1/jobs/cur_ingestion/trigger` once.
3. `GET /api/v1/jobs/ingestion-status` → note `record_count`.
4. `docker exec numio-postgres psql -U numio -d numio -c "SELECT COUNT(*) FROM cost_records;"` → note count.
5. Compare.

## Environment & context

- **Suspected cause:** `_upsert_batch` in `backend/src/numio/core/cur_service.py` dedupes each parquet batch by `(data_source, line_item_id)` before upsert (see `docs/dev-runbook.md` note on CUR amortized RI/Savings Plan rows). The counter that drives `record_count` likely increments before dedupe.
- **Related code:**
  - `backend/src/numio/core/cur_service.py` — `_upsert_batch`, `_run_cur_ingestion`.
  - `backend/src/numio/jobs/runner.py` — `ingestion_statuses` writer.
  - API handler for `/api/v1/jobs/ingestion-status`.
- **Why it matters for UX:** the Data Ingestion page and any `record_count`-driven progress indicators will inflate by the same factor; users will think more data landed than actually did.

## Acceptance criteria (closure)

- Document the intended semantics of `record_count` (processed vs persisted) in `docs/dev-runbook.md` or the API reference, and make the field match that definition.
- Option A: rename/split into `records_processed` + `records_persisted` and update callers (UI + any scripts).
- Option B: keep the single field, change it to mean "rows persisted", and update the counter to increment post-dedupe.
- A backend unit test asserts that `record_count` for a run equals the delta in `cost_records` rows for that run (or equals the unique-key count of the input batch, depending on chosen semantics).
- No regression in `last_status`, `last_sync_at`, or `error_details` behavior.

## Risks & impact

- Low immediate user impact (data is correct; only the counter is misleading), but this is the kind of metric that underpins dashboards, alerting, and support triage. Getting the semantics right before more callers depend on it is cheap now and expensive later.
