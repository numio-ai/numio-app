# Top bar “Autopilot” pill: clickable with real statuses (Active, Stopped, Needs attention)

**Date:** 2026-04-17

## Observed problem

**Autopilot** in the top header appears **dummy** and is **not clickable**. It must reflect real automation health and allow users to understand and change operational state. Required **statuses** (labels and semantics): **Active**, **Stopped**, **Needs attention** — with interaction appropriate to product rules (view details, acknowledge, or toggle stop/resume as defined by backend).

## Expected vs actual

| | Expected | Actual |
|---|----------|--------|
| Interaction | Pill is a control or opens a popover/menu with status explanation and allowed actions. | Static `StatusPill` with fixed display state. |
| States | UI shows **Active**, **Stopped**, or **Needs attention** based on server/workspace automation state. | Appears cosmetic only. |

## Reproduction steps

1. Open any authenticated screen with `SlimTopBar`.
2. Locate **Autopilot** next to **Data**.
3. Click — observe no meaningful automation UI (compare with **Header.jsx** if a richer pattern exists elsewhere).

## Environment & context

- **Related code:** `frontend/src/components/SlimTopBar.jsx` (non-interactive Autopilot), possibly `frontend/src/components/Header.jsx` / `frontend/src/api/workspace.js` (`getAutomationStatus`, `updateAutomationStatus` or equivalents).
- **Backend:** Confirm whether `/api/v1/workspace/automation` (or similar) already exposes status and mutations; task includes wiring or explicit “backend missing” follow-up.

## Acceptance criteria (closure)

- **Clickable:** Autopilot opens a popover, drawer, or navigates to a small panel — consistent with **Data** pill UX — showing current status and short explanation.
- **Three states:** Surface **Active**, **Stopped**, and **Needs attention** from real API data; map unknown/error to **Needs attention** or an explicit error state (document mapping in PR).
- **Actions:** Any user-facing state change the product allows (e.g. pause/resume) must call the backend and optimistic UI must reconcile with server response; if backend is read-only initially, UI must only show status + link to docs/settings (no fake toggles).
- **Accessibility:** Keyboard and `aria` labels reflect live status text, not hard-coded “Active” only.

## Risks & impact

- False sense of automation control or misleading green status when jobs are failing; parity with **Needs attention** when ingestion/automation rules fail.

## Non-goals (for this ticket)

- Full Autopilot feature surface (recommendation execution, policies) — only header status honesty and minimal interaction.
