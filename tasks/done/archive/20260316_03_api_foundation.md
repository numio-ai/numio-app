# API Foundation: Configuration, Scaffolding, Error Handling, and Logging

## Problem Statement

The backend lacks the foundational API infrastructure needed to build features on top of: there is no structured configuration management, no consistent API response format, no global error handling, and no structured logging. Every feature that follows will depend on these foundations being in place.

## Scope

**In scope:**
- **Configuration management:** Application configuration via Pydantic Settings, loaded from environment variables and `.env` files. Secrets (database credentials, AWS role ARNs, API keys) must never be committed to the repository. Environment-specific settings (local dev vs production) must be supported.
- **API scaffolding:** REST API under `/api/v1/` with a consistent JSON response format defined via Pydantic schemas. Health endpoint at `/health` returning service status and database connectivity. OpenAPI documentation auto-generated by FastAPI.
- **Error handling:** Global exception handlers that catch unhandled errors and return structured JSON error responses. Error responses must include: an error code, a human-readable message, and a request ID for correlation. Validation errors (from Pydantic) must return clear field-level error details.
- **Logging:** Logging with correlation IDs that tie log entries to specific API requests. Log levels configurable per environment (e.g., DEBUG for local dev, INFO for production).

**Out of scope:**
- Authentication or authorization middleware
- Business logic endpoints (those come in later phases)
- Frontend changes
- Deployment configuration changes
- Rate limiting (Phase 10)

## Acceptance Criteria

1. Application configuration is loaded from environment variables / `.env` files using Pydantic Settings
2. Changing an environment variable (e.g., log level, database URL) changes application behavior without code changes
3. `/health` endpoint returns JSON with service status and database connectivity check
4. `/api/v1/` serves as the base path for all REST endpoints; OpenAPI docs are accessible
5. An unhandled exception in any endpoint returns a structured JSON error response (not an HTML error page or stack trace)
6. Error responses include an error code, message, and request ID
7. Pydantic validation errors return field-level details in the response
8. Every API request generates log entries with a correlation/request ID
9. Log level is configurable via environment variable

## Quality Gates

Prerequisites: Start PostgreSQL and the backend following instructions in [docs/dev-runbook.md](../../docs/dev-runbook.md) ("PostgreSQL for Local Development" and "Development" sections).

### QG1: Health endpoint returns OK with database status
```bash
curl -s http://localhost:8000/health | python3 -m json.tool
```
**Pass criteria:** Response is valid JSON containing `"status": "ok"` and `"database": "connected"`.

### QG2: OpenAPI docs render and list expected API routes
Open http://localhost:8000/docs in a browser.
**Pass criteria:** Swagger UI loads and shows at minimum these endpoints:
- `GET /health`
- `GET /api/v1/cost/summary`
- `GET /api/v1/cost/by-service`
- `GET /api/v1/cost/trends`

### QG3: Validation error returns structured response with field details
The implementation must include at least one endpoint that accepts typed parameters (query or body) so that Pydantic validation can be exercised. For example, if `/api/v1/cost/summary` accepts a `days` query parameter of type `int`:
```bash
curl -s 'http://localhost:8000/api/v1/cost/summary?days=abc' | python3 -m json.tool
```
**Pass criteria:** Response has HTTP status 422 and is JSON containing `error_code`, `message`, `request_id`, and a `details` array where each entry identifies the field name and the validation error.

### QG4: Unhandled error returns structured JSON (not HTML or stack trace)
The implementation must include a debug/test endpoint (e.g., `GET /api/v1/debug/error`) that raises an unhandled exception. This endpoint should only be available when the app runs in a non-production environment.
```bash
curl -s http://localhost:8000/api/v1/debug/error | python3 -m json.tool
```
**Pass criteria:** Response has HTTP status 500 and is JSON containing `error_code`, `message`, and `request_id`. No Python stack trace is exposed in the response body.

### QG5: Logs are structured JSON with request IDs
```bash
curl -s http://localhost:8000/health > /dev/null
```
Examine the log lines printed in the backend's terminal output (the terminal where the backend is running per the prerequisites).
**Pass criteria:** Log entries for the request include a `request_id` value.

### QG6: All tests pass
```bash
cd backend && uv run pytest
```
**Pass criteria:** Exit code 0, no test failures.

### QG7: Linting passes
```bash
cd backend && uv run ruff check .
```
**Pass criteria:** Exit code 0, no linting errors.
