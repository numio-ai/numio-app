# Publish Numio container images to the GitLab Container Registry

## Date
2026-04-16 (revised 2026-04-18: retargeted from GHCR to GitLab Container Registry because the project is hosted on GitLab, not GitHub)

## Context

The rewritten operator runbook (`tasks/active/20260416_01_rewrite_ops_runbook.md`) assumes operators install Numio by pulling pre-built images from a public registry. Today the only distribution channel is private AWS ECR (`scripts/tools/ecr.sh`, `numio-srv` / `numio-ui` under AWS profile `agenture-prod`), which is Numio-internal and cannot be used by a forward-deployed engineer or customer AWS admin.

The project is hosted on GitLab (`gitlab.com:numio-ai/numio-app.git`) and has no GitHub presence. The chosen distribution channel for the operator install surface is the **GitLab Container Registry**, public, driven by GitLab CI.

## Problem

There is no public image for an operator to pull. Any runbook that uses `docker compose pull` against an external registry will fail until this task lands.

## Goals

1. Build and push two public images on release:
   - `registry.gitlab.com/numio-ai/numio-app/numio-srv`
   - `registry.gitlab.com/numio-ai/numio-app/numio-ui`
2. Tag scheme: `:<semver>` (e.g. `0.1.0`, derived from an annotated git tag `vX.Y.Z`), `:<short-sha>`, and a moving `:latest` on the default branch.
3. Images published automatically via GitLab CI on:
   - push of a tag matching `v*` (produces `:<semver>` and `:<short-sha>`)
   - push to the default branch (produces `:latest` and `:<short-sha>`)
4. Images are pullable without authentication (public visibility). Requires the GitLab project visibility set to public and the Container Registry set to "Everyone" under **Settings → General → Visibility, project features, permissions**.

## Scope

- GitLab CI pipeline (`.gitlab-ci.yml`) to build + push.
- Image metadata (OCI labels: `source`, `revision`, `created`, `version`, `title`) baked at build time.
- Hardening: `.dockerignore` in `backend/` and `frontend/` to prevent local state (`.env*`, `.venv`, `node_modules`, logs) from entering the build context.
- CI guard that fails the pipeline if `.env` or `.env.*` files appear in the build context.
- Tag scheme and `latest` policy documented in `CONTRIBUTING.md`.
- Ops runbook (`docs/ops-runbook.md`) updated: all `ghcr.io` references replaced with `registry.gitlab.com/numio-ai/numio-app/...`, and the release-download URLs for the operator install artifacts (`docker-compose.yml`, `.env.example`, `numio-ctl.sh`) retargeted to GitLab release assets.

## Out of scope

- Image signing / attestation (capture as a follow-up).
- Mirroring to other registries (ECR, Docker Hub, GHCR, Quay).
- Existing ECR push path for internal deploys — leave in place for now.
- Actually creating a `v0.1.0` release tag. This task lands the pipeline; cutting the first release is a separate action.

## Acceptance criteria

1. A `v*` tag push produces two new image versions under `registry.gitlab.com/numio-ai/numio-app/numio-srv` and `.../numio-ui`, visible on the project's **Packages & Registries → Container Registry** page.
2. A push to the default branch produces / updates `:latest` and `:<short-sha>` for both images.
3. `docker pull registry.gitlab.com/numio-ai/numio-app/numio-srv:<tag>` and the `numio-ui` equivalent succeed from a host with no GitLab authentication.
4. Each pipeline run completes in under 10 minutes on the default shared runner.
5. `CONTRIBUTING.md` documents the tag scheme and which branch / tag promotes to `:latest`.
6. `docs/ops-runbook.md` no longer contains `ghcr.io`; operator install commands reference the GitLab registry and GitLab release assets.

## Validation steps

1. On a clean host with no GitLab login:
   ```
   docker pull registry.gitlab.com/numio-ai/numio-app/numio-srv:latest
   docker pull registry.gitlab.com/numio-ai/numio-app/numio-ui:latest
   ```
   Both succeed.
2. `docker inspect registry.gitlab.com/numio-ai/numio-app/numio-srv:latest` shows the expected `org.opencontainers.image.source`, `.revision`, `.created`, and `.version` labels pointing at the published git commit.
3. Induce a `.env` leak (temporarily place a file named `.env.test` in `backend/`) on a branch pipeline and confirm the pipeline fails at the leak-guard step. Remove the file before merging.

## Risks

- **Risk:** secrets (DB credentials, API keys) baked into the image during the build. **Mitigation:** `.dockerignore` excludes `.env*`; CI leak-guard step fails the pipeline if any `.env`-like file is present in the build context before `docker build`.
- **Risk:** public image exposes internal code. **Mitigation:** the repository itself is already published under `gitlab.com/numio-ai/numio-app` — publishing the built image is consistent with current source visibility. Confirm project visibility + registry visibility are both public before enabling `v*` tag builds.
- **Risk:** GitLab Container Registry visibility is per-project and, under some GitLab editions, additionally per-registry — a private registry on a public project silently returns 401 to unauthenticated pulls. **Mitigation:** validation step 1 is the definitive check; run it from a host that has never authenticated to gitlab.com.
