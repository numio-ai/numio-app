# Background jobs skip all accounts when `aws_accounts.status` is not `active`

## Date

2026-04-16

## Observed problem

After connecting an AWS account and validating credentials, background jobs (`cur_ingestion`, `sample_ingestion`, etc.) record `job_runs.status = 'skipped'` with no `job_run_accounts` rows. No cost data is ingested into `cost_records`, even though the worker process and scheduler appear healthy.

## Expected vs actual

- **Expected:** Accounts that have completed successful connectivity validation are eligible for scheduled and on-demand jobs, or the product clearly documents a separate “activate for jobs” step that sets the status the runner uses.
- **Actual:** `run_job` loads accounts with `AwsAccount.status == "active"` only (`backend/src/numio/jobs/runner.py`). The account lifecycle sets `disconnected` on create (`backend/src/numio/db/aws_account_repository.py`) and `connected` after `validate_connectivity` succeeds (`backend/src/numio/core/aws_service.py`). The value `active` is not set by that flow, so the account list is empty, `run_job` short-circuits with `skipped`, and ingestion never runs.

## Reproduction steps

1. Start local dev: `./scripts/numio-dev.sh run all` (or at least postgres, backend, worker).
2. Ensure default workspace exists and apply migrations: `./scripts/numio-dev.sh migrate`.
3. Register an AWS account via API or UI so that connectivity validation succeeds and `aws_accounts.status` is `connected`.
4. Start or wait for the worker; optionally `POST /api/v1/jobs/cur_ingestion/trigger` as an admin.
5. Query:

   ```sql
   SELECT status FROM aws_accounts;
   SELECT job_type, status FROM job_runs ORDER BY started_at DESC LIMIT 5;
   SELECT COUNT(*) FROM job_run_accounts;
   SELECT COUNT(*) FROM cost_records;
   ```

6. Observe: `aws_accounts.status` is `connected`, recent `job_runs` are `skipped`, `job_run_accounts` has no new rows for those runs, `cost_records` count unchanged.

## Environment & context

- **Repo:** `numio-app` backend.
- **Evidence from investigation:** Large number of `skipped` runs with zero per-account results; single real AWS account row with `status = connected`; `cost_records` at zero while worker log shows scheduler started.
- **Related docs:** `docs/dev-runbook.md` — Troubleshooting section documents the symptom and a dev-only workaround until this bug is fixed.

## Risks & impact

- **Severity:** High — CUR and other per-account jobs silently do nothing in common setups; operators and developers may assume AWS or the worker is broken.
- **Data:** No cost data in `cost_records` despite a “connected” account.
- **Observability:** `skipped` runs look like a no-op success path unless `job_run_accounts` and account status are inspected.

## Acceptance criteria (for whoever implements the fix)

- A newly validated / connected account is included in `run_job` account selection without requiring a manual SQL `UPDATE` or an undocumented status value.
- Behaviour is covered by an automated test (e.g. job run with a `connected` account is not `skipped` solely due to status vocabulary).
- Developer-facing troubleshooting in `docs/dev-runbook.md` is updated if the status model or user-facing activation step changes.
