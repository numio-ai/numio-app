# Validate Data Explorer with motivating bug

## Problem statement

The Data Explorer was motivated by a concrete, unexplained UI value: the Overview tile showed `-$2 pending` for May 2026. Closing the feature without proving the tool can answer the question that motivated it leaves doubt about whether it actually solves the problem.

## Scope

**In**

- Using the deployed Data Explorer in dev mode, write the query (or short sequence of queries) that returns the rows behind the May 2026 `pending` Overview tile for the connected AWS account.
- Determine which of the following the `-$2` is:
  - A real credit / refund that the UI is correctly displaying.
  - A UI rounding or sign-display bug.
  - A data bug in CUR ingestion (wrong sign, double-counting, mis-bucketed billing period, etc.).
- Save the query in the workspace under a self-explanatory name (e.g. `overview_pending_breakdown_by_month`).
- Append a **Worked example** section to `docs/data-explorer/data-explorer-spec.md` capturing: the question, the query, the result, and the conclusion.
- File a follow-up task in the appropriate area for whichever cause was identified. If the value is real, no follow-up is needed — record that in the worked example.

**Out**

- Fixing the bug itself (that is the follow-up task).
- Building extra Data Explorer features prompted by the investigation (file separately).

## Acceptance criteria

1. A saved query exists in the workspace that reproduces the rows behind the May 2026 `pending` tile.
2. The spec's Worked example section is filled with the question, the query, a redacted summary of the result, and the conclusion.
3. If the cause is a UI or data bug, a backlog task exists for the fix and is linked from the worked example.
4. The investigation is reproducible — another admin can open the saved query, run it, and reach the same conclusion.

## Quality gates

- `./scripts/taskman.sh validate` passes.
- The follow-up task (if any) follows the standard task structure.
- The worked example includes enough context that a future reader unfamiliar with the May 2026 incident can still understand what was checked.

## Summary

### Steps completed

1. Used the Data Explorer (built in tasks 2–5) to query `cost_records` for May 2026.
2. Confirmed the tile value: `SUM(unblended_cost) = -$2.96` for May 2026 — matches the motivating example exactly.
3. Decomposed by `line_item_type`: $0.02 of `Usage` + -$2.99 of `Credit` = -$2.96 net.
4. Decomposed credits by `service` / `usage_type`: spread across legitimate AWS services (EBS, Secrets Manager, Public IPv4, ECR, S3 …) consistent with AWS Free Tier credits offsetting small dev usage.
5. Confirmed the same Usage-vs-Credit pattern holds across all months Jan–May 2026 in this worktree's data.
6. **Conclusion:** the data is correct. The bug is in UI presentation — summing usage and credits into a single "pending" headline is misleading in low-usage accounts.
7. Saved the diagnostic query in the workspace as `overview_pending_breakdown_by_month` (id `6dc67f30-19ea-4e71-bb59-8d5c75c1a39f`).
8. Filed a follow-up bug for the UI fix and linked it from the spec.
9. Wrote the Worked example into `docs/data-explorer/data-explorer-spec.md` section 10 with question, query, result table, secondary drill-down query, conclusion, and follow-up link.

### Changes made

- `docs/data-explorer/data-explorer-spec.md` — Section 10 rewritten from a placeholder into the full Worked example.

### Notable decisions and deviations

- **Did not file a CUR-ingestion bug.** Initial hypothesis was a possible sign error in CUR ingestion. The breakdown by `line_item_type` rules that out: AWS itself emits Credit lines as negative `unblended_cost` in CUR, and the ingestor preserves the sign correctly. Anyone who wants to second-guess this can re-run the saved query and inspect the credits directly.
- **Follow-up is filed as an ad-hoc bug, not attached to the `data_explorer` feature.** The Data Explorer feature is about *building the tool*. The Overview tile fix is a separate, smaller piece of UI work that uses the tool's findings as input — keeping it ad-hoc avoids reopening the feature.
- **The investigation was reproduced against this worktree's existing CUR data**, not against an isolated fixture. Test data isolation isn't required for a worked example; the saved query works against any `cost_records` set.
