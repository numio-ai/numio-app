# Read-only Postgres role for Data Explorer

## Problem statement

The Data Explorer must execute arbitrary user-supplied SQL without risk of mutation. The tightest enforcement is a dedicated Postgres role with `SELECT`-only grants — Postgres rejects writes regardless of what the application does. App-level SQL parsing is fragile and rejected by the spec.

## Scope

**In**

- Alembic migration that:
  - Creates role `numio_readonly` with `LOGIN` and a password sourced from settings.
  - Grants `USAGE` on schema `public`.
  - Grants `SELECT` on all existing tables in `public`.
  - Sets default privileges so future tables are also `SELECT`-able by `numio_readonly`.
  - Provides a clean downgrade that revokes grants and drops the role.
- Backend settings entries for the read-only DSN (host, db, user, password, port — typically reusing host/db/port and overriding user/password).
- A separate SQLAlchemy async engine + session factory bound to the read-only role, used only by the Data Explorer query endpoint.
- Container/compose wiring so the password is provisioned in local dev (env var with sensible default) and documented for ops.

**Out**

- The query endpoint itself (next task).
- Saved-queries table (separate task).

## Acceptance criteria

1. After `./scripts/numio-dev.sh migrate`, role `numio_readonly` exists in the database and can authenticate with the configured password.
2. `numio_readonly` can `SELECT` from every Numio table (current and any added later via Alembic).
3. `numio_readonly` cannot `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `ALTER`, `CREATE`, or `DROP`. Each is rejected by Postgres with the standard permission error.
4. The downgrade migration leaves the database clean (no orphan role, no orphan default privileges).
5. The backend exposes a typed accessor (e.g. `get_readonly_session()`) that opens a session against the read-only role. Smoke test confirms a `SELECT 1` succeeds and a `CREATE TABLE` raises.

## Quality gates

- `cd backend && uv run pytest` passes, including a new test that asserts the role's permission boundary.
- `cd backend && uv run ruff check .` and `ruff format .` clean.
- Migration upgrade and downgrade both run cleanly on a fresh database.
- Dev runbook updated if any new env var is required.

### Notable decisions and deviations

- **Dropped explicit `GRANT CONNECT ON DATABASE`.** Postgres's `format('%I', db_name)` clashed with psycopg's `%`-substitution, and templating the DB name through Python added complexity. PUBLIC has CONNECT by default, so `numio_readonly` inherits it; this keeps the DDL portable across DB names (dev `numio`, test `numio_test`). Spec updated.
- **Used `DROP OWNED BY` in downgrade** instead of enumerating REVOKEs — works regardless of how many tables exist at downgrade time.
- **DDL is held in plain Python helpers**, not embedded in the migration body. Tests can apply the same statements without invoking Alembic, which the test infrastructure does not run.
- **Not fixed (pre-existing):** worktree DB is on legacy alembic revision `c1a8b9d2e3f4`, predating the consolidated baseline. `numio-dev.sh migrate` errors out for everyone here — orthogonal to this task. The new migration is mechanically correct (proven by the test suite running its helpers).
