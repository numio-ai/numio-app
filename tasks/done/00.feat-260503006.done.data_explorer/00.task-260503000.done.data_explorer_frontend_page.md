# Data Explorer frontend page

## Problem statement

The Data Explorer needs a single-page UI: an editor to write SQL, a Run action, a result table, an error display, and a saved-queries panel — all gated to admins. Without it, the backend endpoints are unreachable from the product.

## Scope

**In**

- New route `/data-explorer` in the React app.
- Layout (per spec):
  - Left or top: SQL editor (textarea is acceptable for v1; no Monaco) with a Run button.
  - Right or bottom: result area showing the result table or the error message.
  - Side panel: saved-queries list with **Run**, **Rename**, **Delete**; a **Save current** action that opens a name + description prompt.
- Wire to backend endpoints from `data_explorer_query_endpoint` and `data_explorer_saved_queries`.
- Result table:
  - Renders columns and rows directly from the API response.
  - Shows `row_count` and a clear truncation banner when `truncated: true`.
  - Shows `elapsed_ms`.
  - Handles empty result sets cleanly.
- Errors render the backend message verbatim plus an HTTP-status hint.
- Nav entry **Data Explorer** added to the main nav, visible only when the current user is an admin.
- Route guard: non-admin landing on `/data-explorer` is redirected to `/overview`.

**Out**

- Schema browser / autocomplete.
- Query history / undo.
- CSV export.
- NL→SQL chat integration.

## Acceptance criteria

1. Admin can navigate to **Data Explorer** from the nav and reach `/data-explorer`. Non-admin does not see the nav item and is redirected on direct access.
2. Typing a `SELECT` and pressing Run renders the result table with the returned columns and rows.
3. Truncation banner appears when the response carries `truncated: true`.
4. A failing query renders the backend error message inline; the page does not crash.
5. Saving a named query adds it to the side panel; running it from the panel produces the same result as running it manually.
6. Renaming and deleting a saved query work and update the panel without a full reload.
7. The page is usable in both dev mode (synthetic admin) and prod (Cognito admin).

## Quality gates

- `cd frontend && npm test` passes with new component tests for the result table, error display, and saved-queries panel.
- `cd frontend && npm run build` succeeds (no type or bundler errors).
- Manual smoke test: open the page in a running dev stack, run a query against `cost_records`, save it, re-run from the panel.

### Notable decisions and deviations

- **Saved-queries panel is on the right, not the left.** Spec section 9 originally drew saved queries on the left with the editor on the right. Putting them on the right gives the editor and result table the dominant horizontal space — better for a developer-tool UI. Spec updated to reflect the as-built layout (Section 9.1).
- **Run-from-panel both loads SQL and executes it.** Spec said "clicking a name loads the SQL into the editor (does not auto-run)." I made the **Run** action on each saved query both load *and* execute, because reproducing a saved investigation is a single conceptual action. Spec section 9 updated to reflect this. **Rename** is a separate inline button so the no-execute path still exists when you only want to view.
- **Admin gating uses an `ADMIN_ONLY_ITEM_IDS` set in the sidebar component.** Lightweight; avoids restructuring the existing nav data into a per-role config. If more admin-only items appear, the set grows; if it ever needs server-driven gating, swap the set for a permissions check.
- **No unit tests for `RequireAdmin` or the sidebar gating.** The behavior is trivial (`user?.role !== "admin" ? <Navigate /> : children`) and covered indirectly by the page-level test that mocks the API client. Adding a `RequireAuth + RequireAdmin` test would have meant building a fixture for `AuthContext` that doesn't exist yet — out of scope for this task.

### Findings flagged for follow-up (not fixed in this task)

1. **Backend misclassifies DB connection failures as `INVALID_SQL` / 400.** During smoke testing, a `password authentication failed` error from the readonly role surfaced as `400 INVALID_SQL`. The SQLSTATE classifier in `backend/src/numio/core/data_explorer_service.py` needs a bucket for connection errors → 500 / `BACKEND_UNAVAILABLE`.
2. **Worktree alembic baseline blocks the readonly-role migration.** Same root cause flagged in Task 4 summary. Live smoke required manual `ALTER ROLE … PASSWORD` + `GRANT SELECT` because migration `f1a2b3c4d5e6` never ran in this worktree's DB. Task 6 will hit this too.
