# POST /tags/apply{,/preview} with risky-write gate + TagGovernance wiring

## Problem statement

`tag_write_service` can write tags but nothing exposes it. Feature `tag_management` needs preview + apply endpoints with a risky-write gate, and the TagGovernance page wired to them (replacing its mock-driven local state). Spec §8.1, §9.1.

## Scope

In scope:
- `POST /api/v1/tags/apply/preview` (viewer+): returns `{ risky, reasons, affected_resources }`; no write.
- `POST /api/v1/tags/apply` (admin/editor): body `{ changes, rationale?, confirm_risky? }`; calls `tag_write_service`; returns `ActionEventResult`.
- Bulk cap: >100 changes → HTTP 400 `code=BULK_LIMIT_EXCEEDED`, no AWS calls.
- Risky rule (mirror `mockTagManagement.js` `isRiskyWrite`): any affected resource has `env` in (`prod`,`production`) OR aggregate latest-period monthly cost > $1000. If risky and `confirm_risky!=true` → HTTP 400 `code=RISKY_WRITE_NOT_CONFIRMED`.
- Wire `frontend/src/pages/TagGovernance/TagGovernancePage.jsx`: single edit → `POST /tags/apply`; bulk → preview first, on `risky=true` open new `RiskyWriteModal`, on confirm `POST /tags/apply` with `confirm_risky=true`. `partial_failure` → toast listing failed resources + AWS error codes. Remove mock-driven local override state.

API-boundary constraints (the `tag_write_service` from task 4 does NOT enforce these — the endpoint must):
- **Map `BulkLimitExceeded` → HTTP 400 `code=BULK_LIMIT_EXCEEDED`** (the service raises it before any AWS call; A2 depends on this).
- **Dedupe `(resource_id, tag_key)`** in the request before calling the service — the service does not dedupe, so duplicates create duplicate audit rows.
- **Reject empty-string `value=""`** (the service would treat `""` as a valid set). Decide remove-vs-reject; reject is safer.
- **Derive `operation_type`**: pass `tag_remove` when every change has `value=None`, else `tag_apply` (the service default is `tag_apply`).
- Service entry points: `apply_tag_changes(session, workspace_id, changes: list[TagChange], actor, rationale=None, *, operation_type=...)` and `apply_single_tag(...)`; `TagChange(resource_id: UUID, tag_key, value|None)` and `ActionEventResult(event_id, status, summary)` live in `core/tag_write_service.py`.

Out of scope:
- MCP (task `tag_mcp_tools`).
- Schema conflicts tab (task `aws_org_tag_policy_sync`).

## Acceptance criteria

A1 (=feature A2,A3). Single + 50-resource bulk apply succeed; audit parent+children recorded; partial failures surfaced.
A2 (=feature A4). 150-resource bulk → HTTP 400 `BULK_LIMIT_EXCEEDED`, no AWS calls.
A3 (=feature A5). Preview on a `env=production` target returns `risky=true`; apply without `confirm_risky` → 400 `RISKY_WRITE_NOT_CONFIRMED`; with it, proceeds.

### Notable decisions / deviations
- **Preview-first for single edits too** (task body line 21 said single → apply directly). A single `env=production` write would otherwise hit the backend's `RISKY_WRITE_NOT_CONFIRMED` 400 with no way to confirm. Uniform preview-first drives the risky modal in both cases. Spec §9.1 updated to match.
- **Result surfaced as an inline panel inside the modal**, not a global toast primitive (none exists in the codebase). The acceptance criterion — failed resources + AWS error codes visible — is met; the data is read from the action-event detail because `result.summary` carries only counts.
- **Browser smoke is bounded by mock-data resource IDs.** The Resources table is still the IA v2 mock dataset (non-UUID ids), so a live apply 422s on `resource_id`. Verified in-browser: modal mounts, form usable, request fires, error surfaces. Success / risky-modal / partial-failure *rendering* is covered by unit tests + the live-backend response-shape smoke. End-to-end apply needs real `CloudResource` rows (connected account + inventory sync) — backing the list with live `/resources` data is out of scope here (task body line 70).
- **API-guide + spec edits** landed with this task because the backend half didn't ship them.
