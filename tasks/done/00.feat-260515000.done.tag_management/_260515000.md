# Tag management — write back to AWS, AWS Org sync, drift detection, audit split

## Problem statement

Numio reads AWS resource tags daily and evaluates them against `tag_policies`. It cannot write tags back, has no model of AWS Organizations Tag Policies, and treats `prod` and `production` as two valid enum values. The TagGovernance UI is built on mocks. Customers cannot fix tagging issues from inside Numio, and the Guardian-of-Transparency capability in the vision doc cannot close the detect → fix → measure loop.

The MVP target from the vision doc is moving tag compliance from 61% to 91% in 30 days. That target requires a working write path, AWS Org awareness, and drift detection.

## Objective

A workspace admin opts a connected AWS account into tag writes via the Guided CFN flow, fixes tags on one or many resources from the TagGovernance page with explicit risky-write confirmation, sees AWS Organizations Tag Policies surfaced alongside Numio's own policies, declares value equivalence groups so drift is detected, and audits every Numio-initiated write to AWS in a stream separate from Numio's own configuration audit log.

## Scope

In scope:
- Tag write to AWS via `resourcegroupstaggingapi:TagResources`, single + bulk, cap 100 resources per operation
- New `NumioTagWriterRole` provisioned via the existing Guided CFN flow with an opt-in checkbox
- AWS Organizations Tag Policy ingestion (read-only), auto-detect of the management account, daily sync
- Drift detection via per-rule equivalence groups, new `drift` status in compliance results
- Audit table split: rename `audit_events` → `audit_config_events`; new two-level `audit_action_events` + `audit_action_event_items`
- Risky-write detection (production tag OR aggregate cost > $1000) with explicit confirmation
- MCP tools: `list_tag_keys`, `get_resource_tags`, `apply_tags`, `list_tag_conflicts`, `get_tag_coverage`
- Frontend audit page split into Setup / Operations tabs; TagGovernance page wired to live endpoints

Out of scope (tracked separately):
- Multi-cloud tags (GCP, Azure) — vision doc Phase 2
- Tag value suggestions / peer inference — deferred per design discussion 2026-05-15
- Two-way Numio → AWS Org reconciliation (pushing schema upstream)
- Tag history UI timeline — backend captures it via audit; UI work is a follow-on
- Per-service IAM permission narrowing for the writer role
- Credential encryption at rest — separate roadmap item

## Acceptance criteria

A1. Admin enables tag writes via a Guided CFN run on a connected account. After stack apply and Verify pass, `aws_accounts.tag_writer_role_arn` is populated for that account. The TagGovernance page shows the account as tag-write-enabled.

A2. Admin edits one tag on one resource from TagGovernance and clicks Apply. Within 10 seconds the tag is set on the AWS resource (verified by `resource_inventory_sync` next cycle or by reading via AWS console). One `audit_action_events` row exists with `status=success` and one child item carries before / after / `aws_request_id`.

A3. Admin applies one tag change to 50 resources in one operation. The operation completes within 60 seconds. The audit shows one parent row + 50 child rows. The UI surfaces the parent status and any partial failures.

A4. Admin attempts a bulk apply touching 150 resources. The endpoint rejects with HTTP 400 and `code=BULK_LIMIT_EXCEEDED`. No AWS calls are made.

A5. Admin applies a tag change where at least one affected resource has `env=production`. `POST /tags/apply/preview` returns `risky=true`. `POST /tags/apply` without `confirm_risky=true` is rejected with HTTP 400 and `code=RISKY_WRITE_NOT_CONFIRMED`. The same call with `confirm_risky=true` proceeds.

A6. With an AWS Organizations tag policy configured in the customer's management account, the daily `aws_org_tag_policy_sync` job populates `aws_org_tag_policy`. `GET /aws-org-tag-policy` returns the synced rows. `GET /tags/schema/conflicts` returns conflicts when a Numio `tag_policy_rule.tag_name` matches an AWS Org key but `required` or `allowed_values` differ.

A7. A tag policy rule with `equivalence_groups=[["production","prod"]]` causes resources tagged `env=prod` to receive `status=drift` in the next compliance audit, not `compliant` and not `invalid_value`. The `/compliance/non-compliant` endpoint includes drift rows.

A8. `/api/v1/audit-config-events` returns the same shape and data as `/api/v1/audit-events` did before the rename. `/api/v1/audit-events` returns HTTP 404. All `@audit_trail`-decorated endpoints continue to write audit rows under the new table name.

A9. The frontend `/govern/audit` page shows two tabs: Setup (default) and Operations. Setup queries `/audit-config-events`. Operations queries `/audit-action-events`. Clicking a row in Operations opens a drawer showing the parent event and all child items.

A10. From a running MCP client, calling `list_tag_keys`, `get_resource_tags(arn)`, `apply_tags(arn, tags)`, `list_tag_conflicts`, and `get_tag_coverage` returns sensible structured responses. `apply_tags` on a risky target without `confirm_risky=true` returns `{ status: 'rejected', reason: 'risky_write_not_confirmed' }`.

## Summary

All 9 tasks are in `tasks/done/`. The feature closes the detect → recommend → write → audit loop for AWS tags: an admin can fix tags on resources from inside Numio with explicit risky-write confirmation, see AWS Organizations tag policies and conflicts alongside Numio's own, have value drift flagged, and audit every Numio-initiated write to AWS in a stream separate from configuration changes. AI agents reach the same surface over MCP.

### Cross-cutting decisions (facts not in any single task)

- **Org sync is coupled to the tag-writer role.** The `organizations:*` read permissions live on `NumioTagWriterRole` (spec §6.1), so management-account detection assumes `tag_writer_role_arn`; accounts without it are skipped with zero AWS calls. Org Tag Policy sync therefore requires tag writes enabled on the management account.
- **Non-org behavior is a no-op, not a persistent flag.** `AWSOrganizationsNotInUseException` ends sync gracefully (logs, upserts nothing, raises no failure). No `workspaces.is_on_org` column was added — a flag would need a clear-when-customer-joins lifecycle, and per-account detection is negligible idle work.
- **`equivalence_groups` are API-settable, no UI.** They round-trip through `POST`/`PUT /tag-policies`; the policy editor has no control for them in MVP (out of scope per task 7).
- **Risky-write rule is shared** by the HTTP path and MCP (`core/tag_risk.assess_risk`); single source of truth.
- **TagGovernance resource table stays on mock data.** Wiring it to live `/resources` was explicitly out of scope (task 5); the Apply flow is live, the grid is not.
