# Synthetic platform and operations data for mock mode

# Synthetic platform and operations data for mock mode

## Problem statement

The `mock_backend_switch` feature runs the full Numio UI from synthetic data with no backend, for customer demos. Synthetic data is split into one core task plus three domain tasks. This is the PLATFORM & OPERATIONS domain: every UI surface outside the cost and governance domains. Without this dataset, settings, integrations, onboarding, the authenticated session, jobs, audit, notifications, chat, and data explorer screens render empty or break in mock mode. The data must be plausible and must agree with the cost and governance datasets — the AWS accounts a demo viewer sees on the Integrations screen must be the same accounts that appear in cost charts and governance findings.

## Scope

In scope — generate synthetic platform/ops data covering the response shapes returned by these frontend API modules:

- `frontend/src/api/workspace.js` (22 functions): workspace settings, user list, API keys (own + all), automation toggles (global + per-domain), workspace identity info, the AWS accounts integration list, notification preferences.
- `frontend/src/api/onboarding.js` (6 functions): onboarding feature flags, CloudFormation template payload, in-progress onboarding state and step progress.
- `frontend/src/api/auth.js` (4 functions): the authenticated user / session ("me").
- `frontend/src/api/jobs.js` (4 functions): job types, job-run history, per-account ingestion status.
- `frontend/src/api/inbox.js` (2 functions): inbox badge counts (unread / triage / critical).
- `frontend/src/api/chat.js` (5 functions): chat sessions and message history.
- `frontend/src/api/dataExplorer.js` (5 functions): query results and saved queries.
- `frontend/src/api/dashboard.js` (audit + notification functions): notifications, notification unread count, audit config events, audit action events (with child items).

Additional in-scope requirements:

- Build ON the shared canonical entities exported by the `synthetic_data_core` task: the SAME canonical AWS accounts, services, regions, and time window. The accounts in the integration/accounts list ARE the canonical accounts; every account referenced by ingestion status, job history, and audit records is one of those canonical accounts.
- Inherit the core's deterministic seeding so two generations produce identical output.
- Place all artifacts under `frontend/src/mocks/`; reuse or extend existing mock files there.

Out of scope (owned by sibling tasks):

- The mode switch / dispatch seam (`switch_dispatch_seam`).
- The shared canonical entities, generator, and consistency harness (`synthetic_data_core` — this task depends on it).
- The cost domain dataset and the governance domain dataset.
- Wiring data into the API modules (`endpoint_coverage`). This task does NOT edit `frontend/src/api/`.
- Automated tests and documentation.

## Acceptance criteria

1. Platform/ops shape coverage: the dataset provides a synthetic response for every platform/ops shape returned by the API modules listed in Scope. Each value structurally matches what the corresponding frontend function returns today.
2. Account consistency: every account in the accounts/integration list is one of the canonical AWS accounts from `synthetic_data_core`. Accounts referenced by ingestion status and job-run history are members of that same integration list — no account appears in jobs or ingestion that is absent from the integration list.
3. Cross-domain consistency: the canonical accounts used here are the same canonical accounts the cost and governance datasets reference. No account ID, service, or region is invented locally outside the core's canonical set.
4. Uses core entities: services, regions, and the time window come from `synthetic_data_core` — they are not redefined in this task's files.
5. Plausibility: values are realistic for a small AWS estate — user roles and statuses, automation toggle states, job statuses and timestamps, ingestion last-sync and record counts, audit actors and actions, notification severities and unread count, chat session titles and message turns, data-explorer column/row results and named saved queries.
6. Determinism: two consecutive generations produce byte-identical output (inherited from the core's seeding).

## Quality gates

- `cd frontend && npm test` passes.
- `cd frontend && npm run build` succeeds.
- Consistency check: accounts in the integration list match the canonical accounts used by the cost and governance domains; ingestion-status and job-history accounts are a subset of the integration list.
- Determinism check: two generations of this dataset are identical.
- No lint gate — the frontend has no lint script.

## Constraints and assumptions

- DEPENDS on `synthetic_data_core`. This task cannot complete before the core's canonical entities, seeded generator, and harness exist. It imports the canonical accounts/services/regions/time window rather than defining its own.
- Data authority is the live frontend response contract: the shapes returned by `workspace.js`, `onboarding.js`, `auth.js`, `jobs.js`, `inbox.js`, `chat.js`, `dataExplorer.js`, and the audit/notification functions in `dashboard.js`. When a field's shape is ambiguous, the live API module wins.
- Existing mock files (for example `mockIntegrations.js`, `mockNotifications.js`, `mockAuditLog.js`, `mockChat.js`, `mockPeople.js`, `mockAccessTokens.js`) are reference-only — useful for plausible values, but not a dependency. This task carries no runtime dependency on `numio-demo`.
- This task produces data only. It does not wire data into API modules and does not edit `frontend/src/api/`.

### Verification (all quality gates pass)
- `npm test`: 445 passed / 44 files (+12 platform tests; no regressions).
- `npm run build`: succeeds.
- Account consistency (AC2/AC3): the integration list's `aws_account_id` set equals the canonical account set exactly; every job-history and ingestion-status account is a member of the integration list; each row's UUID `id` is distinct from its 12-digit `aws_account_id`.
- Shapes: list endpoints use their named key + count; audit action event detail items length == `summary.item_count`; unread count == count of unread notifications; data-explorer rows reference canonical accounts.

### Notable decisions / deviations
- Random-dependent data (job-run record counts, ingestion counts, query result) is precomputed once at module load — the shared seeded RNG is stateful, so building inside the call-time builders would break byte-identity across repeated calls. Builders return the frozen values (the same pattern `cost.js` uses with its fact table). Caught and fixed before first test run.
- `me()` here is the authoritative session user; the Task-1 store seed of `me`/inbox is a scaffold the `endpoint_coverage` task reconciles when it wires handlers.
