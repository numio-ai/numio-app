# IA v2 Send-to-Autopilot confirmation modal — reusable, dry-run gated

## Problem statement

Enabling recurring automation is qualitatively riskier than a one-off action. Today there is no audited approval gate — users can flip a switch without seeing what the rule will actually do. The IA v2 design specifies a high-stakes confirmation modal that re-states evidence, shows the rule in human-readable form, lists safety properties, and offers dry-run-first by default. The modal is used from two entry points (Recommendations and Autopilot + New rule), so it must be a reusable component.

## Scope

In scope:
- A reusable React component `<SendToAutopilotModal recommendation={...} onApprove={({ ruleId, dryRun, approvedBy }) => ...} onCancel={...} />`.
- Modal content sections in order:
  1. Action summary — title, $/mo saved, resource count, scope as code-formatted block.
  2. Evidence checklist — same signals as inline evidence, framed as ticks the user is approving.
  3. Rule preview — terminal-style code block showing the rule DSL (WHEN / DO / THEN / EXCEPT). "Open rule editor →" link closes the modal and navigates to `/autopilot?new=true&prefill={recId}`.
  4. Safety properties — reversibility window, idempotency, manual-review-first-runs, blast-radius cap (one row each).
  5. Dry-run toggle — checked by default with "(recommended)" hint.
- Footer: Cancel · Approve and enable buttons.
- Component imported and rendered from `Recommendations` (Send to Autopilot button) and from Autopilot `+ New rule` (every new rule routes through the same modal).

Out of scope:
- Persisting Approve to a backend — `ia_v2_be_autopilot_rules`.
- Editing the rule DSL inside the modal — only preview + link out.
- Notification or email after dry-run completes.

## Acceptance criteria

A1. Modal renders the five sections in the order specified above; content shape matches the Send-to-Autopilot artboard in `docs/design-mocks/numio-ia-v2/project/Numio IA v2.html` line 102.

A2. Dry-run toggle is checked by default; "(recommended)" hint is adjacent.

A3. "Approve and enable" button click invokes `onApprove({ ruleId, dryRun, approvedBy })` with the toggle's current value and the current user from `AuthContext`.

A4. "Open rule editor →" closes the modal and navigates to `/autopilot?new=true&prefill={recId}`.

A5. Cancel closes the modal with no side effect; `onApprove` is not invoked.

A6. Component is reusable: rendering it from `Recommendations` and from `Autopilot + New rule → From recommendation → Configure` uses the same exported component (verified by import path).

### Notable decisions or deviations

- **`/autopilot?new=true&prefill={recId}` doesn't exist yet** — task 3 (`ia_v2_autopilot`) creates `/autopilot`. The "Open rule editor →" link navigates correctly; the destination 404s in the interim. Same pattern as other v2 link targets.
- **`approvedBy` falls back to `auth.user.id` then `"unknown"`** — `AuthContext` may return `user: null` if `/api/v1/auth/me` fails. The fallback ensures the callback payload is always well-formed for downstream consumers (analytics / audit).
- **Outside-click closes the modal** by checking `e.target === e.currentTarget` on the backdrop. Cleaner than wiring up an `onMouseDown` ref watcher.
- **Rule and safety arrays have fallback values** when a recommendation lacks them. A recommendation without `rule` or `safety` won't crash the modal; it just shows generic placeholder lines.
- **`auth.user.id` UUID used when email is absent** — handles the bypass-mode synthetic admin (`admin@localhost` with `id: "00000000…"`).
- **Test count: 292 → 303** (+11 modal tests).
