# CUR runner regression lock — end-to-end test

# CUR runner regression lock — end-to-end test

## Problem statement

The CUR ingestion path has unit + integration tests but no end-to-end test that exercises `runner.run_job(...)` → `cur_ingestion_job(account_id)` → service-owned session commit → `cost_records` persisted → `JobRun` / `JobRunAccount` / `IngestionStatus` written, all in a single integration. Two historical regressions (missing inner-session commit; batch dedupe collision) shipped silently because no test failed when the bug was reintroduced.

## Scope

In scope:
- Create `backend/tests/test_cur_runner_e2e.py`.
- Reuse `_make_cur_parquet`, `_sample_cur_row`, `account_with_cur`, `db_session`, `default_workspace_id` from existing test infrastructure.
- Patch `_ingest_parquet_file` (or the manifest discovery layer) to short-circuit S3 with the in-memory parquet bytes — same pattern as existing `TestIngestParquetFile` cases.
- Three test cases:
  1. `test_runner_persists_cost_records_end_to_end` — happy path; asserts the full chain.
  2. `test_runner_is_idempotent` — second run keeps row count flat, advances `updated_at`.
  3. `test_regression_lock_canary` — monkeypatches `_run_cur_ingestion` to skip its final `await session.commit()` and asserts the happy-path assertions fail (proves the lock actually detects the regression). Skip via `@pytest.mark.xfail(strict=True)` so a regression-fix accidentally restoring the commit doesn't silently break the canary.

Out of scope:
- Refactoring `cur_service.py` or `runner.py`.
- Adding moto.
- Performance benchmarks.

### Notable decisions or deviations

- **Canary pytest case dropped.** The scope proposed a third test (`@pytest.mark.xfail(strict=True)`) that simulates the missing inner-session commit by monkeypatching. In practice the monkeypatch did not reliably suppress `AsyncSession.commit()` in SQLAlchemy 2.0 async due to interaction between the session factory's lifecycle and `__aenter__` indirection. A brittle xfail-strict canary that silently passes-when-it-shouldn't is worse than no canary. The regression-lock verification is delegated to the manual gate in acceptance criterion A2 and documented in a comment block inside the test file. The two e2e tests *are* the lock — what changed is how the regression is verified during code review.
- Scope item "Reuse `account_with_cur` from existing fixtures" was not used — that fixture flushes (rolls back), while this test requires a committed account so the inner session can see it across the connection pool. Replaced with a local `committed_cur_account` fixture that commits and is cleaned up by `clean_cur_tables`.
